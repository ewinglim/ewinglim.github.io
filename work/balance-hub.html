Balance Hub — one window for everything a designer owns

Every free-to-play project I have worked on has the same quiet problem: the numbers that decide whether the game is any good are scattered across dozens of assets, and nobody can tell you the state of the build without opening all of them. Balance Hub is my answer to that — a single editor window that owns the whole authoring surface and reports what is still wrong before anyone presses Play.

The problem it solves

A data-driven game is a good idea that decays. You start with a couple of ScriptableObject configs so designers can tune values without a rebuild, which works. Then the project grows, and eighteen months later the numbers that define the game live in forty assets across six folders, each edited through Unity's default inspector, with no relationship between them that anyone can see.

Three concrete costs, all of which I have paid:

  • Nobody knows the state of the build. "Is the round the right length?" requires opening five assets and doing arithmetic. So the question gets asked once a month instead of once a day.
  • Missing content is invisible until it fails. Code asks for a sound by id. No clip is mapped. Nothing errors — it just plays silence, and you find out in a playtest, or you don't.
  • Designers ask programmers for permission. Not because the data is locked, but because the default inspector gives no confidence that a change is safe. So changes queue behind whoever wrote the system.

Balance Hub attacks all three with the same move: put the whole authoring surface in one place, and make that place opinionated about correctness.

One window, ten pages

The window is a left-hand page list and a content area — round balance, score model, ingredients, audio, art, prefabs, motion, UI copy, and a build page, with an overview page in front of them all. Ten pages, eight underlying config assets, one search box.

The important design choice is that a page is not a special case in a growing switch. Each page is a self-contained object that declares its own title, draws its own body and reports its own problems. Adding a page is adding a class, and the shell has no knowledge of what any page contains.

The page abstraction

public interface IHubPage
{
    string Title { get; }
    void Draw();                              // its own editing UI
    IEnumerable<Issue> Validate();            // what it thinks is wrong
}

// The shell knows only the interface. It draws the sidebar, routes the
// selection, and asks every page the same question for the overview.
public sealed class BalanceHubWindow : EditorWindow
{
    private readonly List<IHubPage> _pages = new();
    private int _selected;

    private void OnGUI()
    {
        DrawSidebar(_pages, ref _selected);
        _pages[_selected].Draw();
    }

    // The overview page is not special-cased either — it is the union of
    // every page's own validation.
    public IEnumerable<Issue> AllIssues() => _pages.SelectMany(p => p.Validate());
}

That last method is the whole reason the overview page can exist. The summary is not a separate hand-maintained checklist that drifts out of date — it is derived, every time it is drawn, from the same validation each page already runs for itself. There is no second source of truth to forget to update.

Draft — confirm the specifics

Say whether this is IMGUI or UI Toolkit, and why you picked it. If pages are registered by reflection or attribute rather than a hand-built list, that's worth a sentence — it's the difference between "extensible" and "extensible without editing the shell".

Making absence visible

This is the part I would keep in every tool I ever write again. Most validation checks that a value is wrong. The harder and more valuable check is that a value is not there at all, because absence has no field to inspect and throws no error.

The overview's audit table answers four questions of that shape:

  • Which sounds does the code ask for that have no clip? Twenty-five effects and three music tracks, at the time of that screenshot. The consequence is spelled out in the row: the game is silent until they land.
  • Which prefab ids can code request that have no row? Three. A lookup that will return nothing, with no compile-time hint that it can.
  • Which effects still point at placeholder art? Five, found by the PH_ naming convention — a cheap, ugly, completely effective heuristic.
  • Which mixer groups don't exist? Covered below, because the answer is more interesting than a count.

Each row states an area, a state and a consequence in plain language. Not a log line, not an error code — a sentence a designer or producer can read and act on. The audit is written for the person who has to care about it, not the person who wrote it.

The generalisable idea

Enumerate what the code can ask for, enumerate what the data provides, and show the difference. Almost every integration bug I have chased was somewhere in that gap, and the gap is nearly always computable.

Encoding the design brief

The overview does not just print the round timing. It sums the phases, compares the total against the target the design is supposed to hit, and colours the line amber when it misses.

In the screenshot the round runs 28.9–30.9 seconds against a target of about twenty-five. The tool is telling on the build — and that is the point. The timing was never secretly wrong; it was knowably wrong, and before this existed the only way to know was to add up five numbers by hand and remember what the target was.

A tool that stores the design intent alongside the data stops the intent from living only in someone's memory or a document nobody reopens. A number being present is not the same as a number being right, and only one of those two things the default inspector can tell you.

Naming what it cannot do

Unity exposes no scripting API for creating audio mixer groups. They have to be authored by hand in the mixer asset. There is no way to automate it, and no way for the tool to fix it.

So the tool says so, in the audit, as its own row:

The row, verbatim

no mixer groups — the mixer has to be authored by hand; Unity has no scripting API for mixer groups. Without it, mute does nothing.

Three things are doing work there. It states the gap, it explains why the gap cannot be closed automatically so nobody files it as a tool bug, and it names the user-visible consequence so the priority is obvious.

The tempting alternative is to leave it out, because it isn't something the tool can act on. That's how you get a green dashboard on a broken build. A checklist that only lists what it can automate teaches people to trust it exactly as far as it doesn't matter.

Why this is not a games skill

Strip the vocabulary and Balance Hub is an internal admin tool over a typed data store, with schema validation, referential-integrity checking and a health dashboard derived from the same rules. Swap the nouns and it is a CMS admin panel, a feature-flag console, or an ops runbook page.

The four ideas I would carry into any of those unchanged:

  1. Enforce invariants at write time, not read time. A constraint the authoring UI checks costs someone five seconds. The same constraint discovered in production costs a release.
  2. Treat absence as a first-class query. Dangling references and unmapped keys are the most common class of integration failure and the easiest to enumerate. Almost nobody enumerates them.
  3. Derive the summary; never maintain one. Any status view assembled by hand is wrong within a fortnight.
  4. Write for the reader, and include what you can't fix. The audience for a health check is the person who has to make a decision, not the person who wrote the check.

None of that is Unity-specific. It is the difference between shipping a data layer and shipping a data layer somebody else can safely operate.

Trade-offs & regrets

  • The audit runs when you press Re-check, not continuously. That was a deliberate choice — validating every config on every repaint is slow enough to make the window unpleasant — but it means the overview can be stale without saying so. A timestamp on the panel would have cost me ten minutes.
  • Nothing blocks a build. The tool reports; it does not enforce. Wiring the same Validate() calls into a pre-build step would turn advice into a guarantee, and I would do that first on the next one.
  • One window is a bottleneck as well as a feature. Everything routing through a single surface is exactly why it's useful, and also why every new system wants to add a page. Without a rule about what deserves one, this becomes the place where all the mess accumulates.
  • PH_ prefix matching is a convention, not a constraint. It works until someone names a real asset badly. A proper flag on the asset would be correct; the naming heuristic was expedient and I shipped it anyway.

The window

The overview page: round summary at the top, the audit table beneath it, and the eight config assets the window edits at the bottom, so the data behind every page is one click away.
