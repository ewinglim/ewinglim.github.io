Kingsguard TD — a server that owns progress, and a game that still feels instant

Kingsguard TD started life with its progress in PlayerPrefs on the phone. That stops being acceptable once a game has a gacha, an energy timer, rewarded ads and in-app purchases, because anything the phone stores the player can edit, and any roll the phone makes can be re-rolled by killing the app. My part has been the layer underneath the game: a backend where the server owns every player's progress, the client and server run the same rules, and balance can change without an app update.

Note

Kingsguard TD hasn't launched, so nothing here is a production metric — the numbers are test counts and design values. The game's design (shop, retention and idle-reward specs) is the designer's and producer's; the backend, the protocol, the client integration, the tooling and the build pipeline are mine. Code blocks are sketches of the shape, not the production source.

Why the server owns progress

The decision that everything else follows from: the phone is never trusted with balances, unlocks or items. Every change to a player's progress is a command the server runs, and the screens read the server's answer.

  • One save per player, in Cloud Save's protected slot. The phone can read it; only the server can write it. That's enforced by an access policy deployed as config, not by convention — a player writing to Cloud Save directly gets a 403, which I checked against the real service.
  • A fresh, versioned schema with stable ids. Stages and items get permanent ids instead of file names or list positions, so a designer reordering a list can never corrupt a save. Anything derivable is derived — "highest stage cleared" is computed from stage records, never stored.
  • One active device at a time. Boot claims the session; a call from another phone gets "Playing on another device" and a PLAY HERE button. Never an automatic takeover.

One rule book, two compilers

The obvious way to build this is to write every rule twice: once in the game, so a button knows whether you can afford the upgrade, and once on the server, which actually charges you. That gives you two implementations that must agree forever, and they won't.

Instead, every rule that changes progress is plain C# in an assembly marked noEngineReferences — the compiler refuses UnityEngine. The same source files compile into the Unity client and, linked by the server project, into the Cloud Code module. The language is pinned to C# 9, because Unity's compiler is the lower bound.

The contract every rule keeps

// Engine-free, C# 9. Compiled into the client AND the Cloud Code module.
public static class WallRules
{
    // In: the save, the numbers file, a seeded random if it rolls.
    // Out: a value, or an error code. Never an exception, never a partial write.
    public static Result<Upgrade> Upgrade(PlayerSave save, Numbers n)
    {
        int cost = n.Wall.CostAt(save.WallLevel);
        if (save.Gold < cost)
            return Error.NotEnoughCurrency;   // a refusal changes nothing

        save.Gold -= cost;
        save.WallLevel++;
        return new Upgrade(save.WallLevel, cost);
    }
}

Because a refused rule changes nothing, the server can answer a refusal without writing. And because the maths have to match to the last bit, the rule book uses Unity's rounding (halves to even) and the game's float summation order.

The server tests run with dotnet test — no Unity, no cloud. The ones I lean on hardest are invariant tests: six seeds × 1,500 random actions — valid, refused and forged — and after every single step, no balance is negative, every id is unique, every cap holds, and a refused action left the save untouched.

A bug that only exists across two runtimes

Mono writes a float as 0.450000018; .NET writes the same float as 0.45000002. Both read back to identical bits, so values were never wrong — but any comparison of the numbers file as text would disagree. The fingerprint that tells client and server they hold the same numbers hashes float bits, never strings.

Every call takes the same path

One request pipeline runs in three hosts: the deployed Cloud Code module, a local test server inside the Unity Editor, and the test suite. So the thing I test is the thing that ships.

The pipeline, in shape

public async Task<Response> Handle(Request req)
{
    var doc = await store.Read(req.PlayerId);   // save + revision + session + recent answers

    var gate = Gate(req, doc);                  // maintenance · app too old ·
    if (gate != Status.Ok) return Refuse(gate); // another device · numbers changed

    if (doc.Answered(req.RequestId, out var earlier))
        return earlier;                         // a resend is never applied twice

    for (int attempt = 0; attempt < 3; attempt++)
    {
        var result = game.Execute(req.Command, doc.Save, numbers, rng);
        if (!result.Ok) return Rejected(result.Error);      // nothing written

        if (await store.TryWrite(doc, expected: doc.Revision))
            return Ok(result, PatchSince(req.KnownRevision, doc));

        doc = await store.Read(req.PlayerId);   // someone wrote first: re-read, redo
    }
    return ServerError();
}

The property that makes the client simple is the request id. Resending the same request after any failure is always safe, so the client's RETRY button doesn't need to know whether the first attempt landed. A timeout, a dropped connection, a server error — the answer is the same: send it again.

The local test server is the same pipeline saving to a readable JSON file, and it can simulate latency and being offline. To prove the two hosts really are the same, I ran an identical eleven-command script through the in-process pipeline and through the deployed module as a fresh guest: the two saves came out identical apart from one timestamp.

Battles that survive a dead signal

A battle is the one thing that can't stop to wait for the server. So it is split in two:

  1. Start — sent while the hero draft is on screen. The server checks the stage is open, charges energy, and rolls the drop plan: which enemies carry shards, which chests hold runes.
  2. Finish — the client reports only what happened: outcome, wave reached, the wall's HP, which planned drops were collected. The server pays every reward from its own plan.

The server then checks the report: the run exists and is unsettled (a repeat returns the stored result), it arrived within 72 hours, the wave fits the stage, the HP is between 0 and 1, and every chest the client claims was one the server planned. Forged reports are refused and logged with the player id.

The result goes into an outbox — written to a file before it's sent, so it survives the connection dropping and the app being killed, and it's delivered exactly once: now, before the next call, or by the next launch. With no signal, the result screen says "Rewards arrive when you reconnect" and the player moves on. No retry screen between a player and the next battle.

Energy runs on the same principle. The save stores only the amount and when the refill clock started; the refill itself is computed from server time, so changing the phone's clock changes nothing. A battle whose result never arrives gives its energy back.

One edge needed its own design. Cloud Code shuts an idle module down, and the first call after that can take 13–15 seconds. A brand-new player can't stare at that, so on first launch the phone runs the shared start rule on a new save, lets them straight into Stage 1, and queues the start in the outbox under the same run id — the server learns about the battle before its result arrives.

Making a server game feel instant

Server authority has a cost the player feels: every upgrade tap is a round trip. So for the upgrade screens, artifacts and every rune action, the client now runs the command itself, through the very command table the server runs, on a copy of the save. It shows the result immediately, writes the request to the outbox, and tells the server in the background. If the server refuses, the action quietly rolls back.

The client keeps two copies of the save: confirmed, the server's last answer, and shown, the confirmed copy with the waiting actions replayed on top. Screens read the shown copy, so a correct prediction refreshes nothing twice.

The hard part is randomness — you can't predict a roll you don't hold. So the server keeps dice decided ahead in the save: a small stock of seeds per kind of roll (one per hero for mastery draws, one for rune merges, one for rerolls), topped back up to three after every successful command. The client can show three rolls of a kind before the server answers; a fourth waits. Rolls that must never be guessable — gacha pulls, chests — refuse to be predicted and take the normal blocking path.

Proof, not hope: random-walk tests play thousands of steps and, after every instant action — about 7,600 of them — require the client's prediction to equal the server's exactly: the same accept-or-refuse code, the same result, and the same save apart from the server's dice top-up — and a refusal must leave both copies byte-identical. In the Editor, with two seconds of simulated latency, the upgrade screen answers a tap in 36 ms.

The trade-off I signed off on

A player who reads their own save can see — not change — their next roll of each kind. For a single-player progression game that's an acceptable price for taps that never wait. For a competitive game it wouldn't be.

Live-ops without an app update

Designers keep tuning in ScriptableObjects, which stay the source of truth. One button exports every number the server needs into a single file, with a SHA-256 fingerprint; the Cloud Code module embeds that file, so code and numbers always deploy together. The export refuses on anything that would make a number wrong — an unwired source, a duplicate id, an unreadable field. A renamed field becomes a listed problem, never a silent zero.

At boot the client sends the fingerprint it holds. If the server's differs, the answer carries the new numbers; the client takes them before the save that came with them, writes them into its own assets, and caches them for next launch. I rehearsed it end to end: energy cap 30 → 40 and a wall upgrade cost 100 → 160 reached the screens with no new build.

What runs on that foundation, all of it server-authoritative:

  • Server switches per environment — maintenance mode with a message, and a minimum client version that answers "update required".
  • Retention systems — daily login, a daily spin, daily and weekly missions with point chests, and a seven-day event. The server picks the spin segment by weight; the wheel only animates onto the answer. Battle stats that feed missions are clamped against caps scaled by battle length on the server clock — clamped, never refused, so a good run is never punished.
  • Idle rewards — earnings accrue on the server clock with a cap; rune rewards are rolled from a seed stored with the pile, so the preview the player sees is exactly what CLAIM pays.
  • One game clock for every reset — the daily and weekly reset, daylight saving included, worked out in plain arithmetic rather than TimeZoneInfo, because time-zone databases differ between the Editor, phones and the Linux host. Tests pin the reset across both DST switches.
  • Deploys from inside Unity — a Deploy button in the designers' Balance Hub refuses while the numbers file is stale, runs the server tests first, then deploys with the UGS CLI. Production asks twice, and only the producer deploys there.

Purchases and ads, checked server-side

  • Purchases are verified by the server, not the client. Google purchases are checked with the Play Developer API; Apple's signed transactions are verified offline against a pinned Apple root certificate. Each purchase carries the buyer's player tag, so one receipt can't be redeemed on several accounts.
  • Granting is a server-only command. Only the purchase endpoint can issue it; an app that sends it directly is refused. A transaction pays once, and a repeat returns "already paid".
  • A verified purchase is never refused. Shop rules are checked before the store's pay screen. If a paid item can't be applied after all, the player gets a fallback instead of losing money to a rule. Every verified purchase is written to a refund index before it is paid — if that write fails, nothing is paid, and the client only finishes the store transaction once the grant has succeeded.
  • A tool keeps the stores honest. One product list feeds the game, the server and both stores, through a .NET tool that checks and pushes products to Google Play and App Store Connect, and never deletes anything.
  • Rewarded ads on LevelPlay, capped by the server. The phone claims the reward; the server enforces the daily limits. The server can't prove an ad really played — the docs say so rather than pretend — so ad rewards are capped per day instead of trusted.

Status, plainly: the shop's server foundation is built and tested — offers, passes and a season clock — but there's no shop screen yet and every product is off sale. Live receipt checking is waiting on a store service-account key, and the ad network accounts aren't live yet.

Accounts, privacy and store rules

  • Guest first, then link. Google Play Games on Android, Sign in with Apple on iPhone. Game Center is next.
  • Linking never switches silently. If the account being linked already has a save from another phone, the client previews it — a read-only call that doesn't claim the other phone's session — then asks: keep this phone, or load that save, with a second confirmation before anything is lost.
  • Delete my data, end to end. The server deletes the save, analytics deletion is requested, local queues are cleared, and the sign-in account goes last. UGS doesn't revoke Sign in with Apple tokens, which App Store review requires, so the module does it itself: it signs a short-lived ES256 client secret, trades the authorization code, and revokes the token. A failed revoke never blocks the deletion, and no code, token or key is ever logged.
  • Consent before collection. Nothing is sent before the player agrees, declining is exactly as easy as accepting, and I removed Firebase from the new app because it collected at launch, before anyone was asked.

Builds on every push

The game ships through a CI/CD pipeline I built on GitHub Actions, running on the team's own Windows PC and Mac. Every push to the uat branch builds Android and iOS against the matching server environment, uploads to Google Play internal testing and TestFlight with the next free build number, and posts the result to the team. It uses no paid CI minutes — we moved to self-hosted runners after the hosted budget ran out.

The three environments matter more than they look. Developer cheats are server commands that only dev accepts; uat refuses them exactly like production. So QA plays the game players will get, not a debug build with the edges sanded off.

Why this is not a games skill

Take the vocabulary out and this is a transactional backend with an unreliable mobile client — the same checklist as a wallet or a booking app:

  1. Idempotency keys, so retries are safe by construction rather than by careful timing.
  2. Optimistic concurrency on a versioned document, with bounded retries.
  3. An outbox for at-least-once delivery, made exactly-once by server-side dedupe.
  4. Shared domain logic between client and server, enforced by the compiler, and invariant testing with forged inputs.
  5. Config as code across environments, with a kill switch, minimum-version gating and a deploy that runs the tests first.
  6. Consent and deletion treated as features with an order of operations, not as a settings page.

Trade-offs & what isn't done

  • It hasn't met real traffic. The game is in closed testing. There are no load numbers, and the first production deploy is the producer's call.
  • Numbers deploy with code, not Remote Config. That keeps a balance change atomic with the rules that read it, but every tuning change is a deploy. Remote Config is the planned next step.
  • One save document holds everything — no separate economy service. Every command is one atomic write and the invariants are easy to state; the cost is a document that grows and is rewritten on every command. Caps on stored battle history keep it bounded for now.
  • Cold starts are worked around, not fixed. Letting a new player play ahead hides the 13–15 second wake-up; a returning player can still see "Connecting…".
  • The minimum-time-per-wave check is off. It's built, but the threshold is a design decision that hasn't been made, so a plausible-but-fast forged result is currently accepted.
  • Some pieces wait on keys, not code. Apple token revocation and live Google receipt checks are built and tested against fakes, but need store secrets in the server's secret store before they run for real.
